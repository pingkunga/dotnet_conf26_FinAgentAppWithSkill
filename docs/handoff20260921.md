# Handoff — 2026-09-21/22: multi-currency support

## Why this happened

The user pasted `Income: ¤0.00 · Allocated: ¤0.00 · Available: ¤0.00` from `Budgets.razor`/`Home.razor` and
asked why the currency symbol was unreadable. Root cause: `Directory.Build.props` sets
`InvariantGlobalization=true` (deliberately, for smaller/ICU-free container images), which collapses every
culture's number formatting to the invariant culture — whose `NumberFormatInfo.CurrencySymbol` is literally
`"¤"`, not `"$"`. Every `.ToString("C")`/`{value:C}` call in the app inherited this.

While investigating, we found `Transaction.Currency` already existed in the schema (defaulting to `"USD"`)
but was **completely unused** — no UI ever set it, no aggregation ever read it. Rather than a narrow symbol
fix, the user asked for the real feature: free per-transaction currency choice, a "preferred currency" per
user, live FX conversion for totals, and — in a follow-up — currency detection during receipt OCR. This
session's work covers all of it, delivered across two plan-mode rounds (see
`C:\Users\Chatr\.claude\plans\pasted-content-id-b819-income-0-00-keen-haven.md` for the exact approved
plans, if that path is still on this machine).

## What shipped

**Currency display (Step 1)** — `FinanceApp.Core/Formatting/CurrencyFormatter.cs` formats money manually
(`amount.ToString("N2", CultureInfo.InvariantCulture)` + a small code→symbol map: USD `$`, THB `฿`, EUR `€`,
GBP `£`, JPY `¥`, unknown codes fall back to `"CODE "`), since `InvariantGlobalization=true` is staying —
this works *with* that constraint, not around it. Replaces every `.ToString("C")`/`{value:C}` call across
`Budgets.razor`, `Home.razor`, `Transactions.razor`, `Goals.razor`, `ReceiptUpload.razor`, `Chat.razor`,
`BudgetSkill.cs`, `ReceiptOcrSkillFactory.cs`.

**Per-user preferred currency** — `ApplicationUser.PreferredCurrency` (new column, defaults `"USD"`), a
selector on `/Account/Manage`. That page is static SSR, so the selector had to be a plain `<InputSelect>`,
**not** `MudSelect` — MudBlazor's complex inputs render no `name` attribute and silently fail to bind on a
real POST there (the page's two existing approval toggles already work around this the same way, via
`InputCheckbox`). A one-line warning sits next to the selector: changing it relabels existing budgets/goals,
it does not convert their amounts.

**Per-transaction currency** — `Transactions.razor` got a free `MudSelect` currency picker (that page *is*
`@rendermode InteractiveServer`, so `MudSelect` is fine there). Every other transaction-creating path (top-up
on `/`, goal contribution on `/Goals`, `BudgetSkill`'s `add_transaction`/`top_up_funds`/`contribute_to_goal`,
receipt OCR) now defaults to the user's `PreferredCurrency` instead of the entity's hardcoded `"USD"`.

**Exchange rates** — `IExchangeRateService` (`FinanceApp.Core/Abstractions/`) + `FrankfurterExchangeRateService`
(`FinanceApp.Web/Services/ExchangeRates/`, first use of `AddHttpClient` in this codebase). Backed by
api.frankfurter.dev — verified live: no API key, `GET /v1/latest?base=USD&symbols=THB` shape confirmed,
`/v1/currencies` confirms USD/THB/EUR/GBP/JPY are all supported. Caches successful lookups per calendar day
in `IMemoryCache`, and separately keeps a long-TTL "last known good" rate per pair — on an API failure it
returns the stale cached rate rather than failing outright; returns `null` only when nothing is cached at
all. `FakeExchangeRateService` (`Core/Abstractions/`, deliberately in Core not Web — test projects reference
Core/Skills, not Web) is the deterministic test double.

**`ExchangeRateSkill`** (`FinanceApp.Skills/ExchangeRates/`) — a **second** class-based skill, added
alongside `BudgetSkill` so chat can answer "how much is 100 USD in THB". This is additive, not a 5th entry
in the app's firm "4 features → 4 distinct skill types" mapping (spec.md §4) — it reuses the class-based
*type* rather than inventing a new one. Takes `IServiceScopeFactory` (like `BudgetSkill`) and resolves
`IExchangeRateService` fresh per script call — not for user-isolation reasons (it touches no per-user data),
but because `AddHttpClient<...>` registers a transient typed client and `ChatSessionService` holds skills for
the whole Blazor circuit; resolving fresh avoids holding one `HttpClient` instance that long. Wired into
`ChatSessionService.GetOrCreateAgentAsync` via `.UseSkill(exchangeRateSkill)`.

**Aggregation** — `BudgetRepository.GetAllocationSummaryAsync` gained `targetCurrency`/`IExchangeRateService`
parameters, groups income transactions by currency, converts each non-target currency via the service, and
sums only what converted successfully. A `ConversionIncomplete` flag on `BudgetAllocationSummary` is set
(and the unconvertible amount excluded, never guessed at 1:1) when a rate lookup fails — `Budgets.razor`/
`Home.razor` show a warning banner in that case. `GetBudgetStatusAsync` (per-category spent-vs-limit) was
**deliberately not touched** — it's also used by `MonthlySummaryRepository`, which runs inside
`FinanceApp.McpServer`, a separate standing service with its own DI container; fixing it would mean giving
that server its own outbound-internet dependency, which nobody asked for.

**Receipt OCR currency detection** (second round, follow-up question) — `ReceiptOcrSkillFactory`'s vision
prompt now also asks for a `"currency"` field (ISO 4217 code). Confirmed design with the user: **no eager
conversion at OCR time** — a ฿350 receipt for a USD-preferred user records `Amount=350, Currency="THB"`
directly on the `Transaction`, exactly like a manually-entered THB transaction would; conversion happens
downstream via the already-built aggregation/display pipeline, not inside OCR. An unrecognized/hallucinated
currency code falls back to the user's `PreferredCurrency` (same graceful-degradation principle as
`ConversionIncomplete`). New `Receipt.ExtractedCurrency` column records what was actually used; the response
text and `receipt_status` resource reflect it. `/Receipts`' manual-fields form gained a currency picker so a
human can correct a wrong OCR guess.

## Known limitations (by design, not oversights)

- `Budget.LimitAmount` and `SavingsGoal.TargetAmount`/`CurrentAmount` have no `Currency` column — both are
  treated as already being in the user's `PreferredCurrency`. True implicitly before this change too
  (everything was silently USD); now an explicit, documented assumption.
- Changing `PreferredCurrency` re-labels existing budgets/goals, never converts their numbers.
- `BudgetRepository.GetBudgetStatusAsync` (and therefore the MCP monthly-summary skill) keeps the original
  currency-blind `Sum(t => t.Amount)` — deliberately not extended into `FinanceApp.McpServer`.
- Exchange rates are "latest," not historical — a transaction from 3 months ago converts at today's rate.
